# Skate Motion

Skate Motion simulates a skateboard with a seven-body constraint solver and native scene collision queries. It covers pushing, carving, powerslides, ollies and flip tricks, manuals, grinds, pumping, bails and a walking rider. Handling values are estimates and remain open to tuning.

## Requirements

A current s&box editor and map geometry with physics colliders. Runtime code is pure C#; analysis tools are development-only.

## Install

Mount this local library in your game's `Libraries` folder. Package identity: `notpointless.chomnr_sbox_skate_motion`. It has not been published.

## Quick start

### In the editor

1. Add `Skateboard` and a `Rigidbody` to an object above a collidable floor. Keep the physics root at unit scale, +X forward, +Z up.
2. The default setup generates a deck, trucks and four wheels. Add `SkateControls` for a board-only controller.
3. To use any skateboard model, set **Board Model** on the `Skateboard` (a model from the asset browser or a cloud package): its deck, trucks and four wheels are found from the model's own geometry (or its bones), so its trucks steer, its deck leans into turns and its wheels spin, and the board rides on the model's own wheelbase, track, wheel size and height. No armature is needed; separate meshes, one mesh or a rigged model all work (see How it works). For your own parts instead, add `SkateboardRig` on the same object. Assign a deck model and optional wheel model, or assign all four existing wheel objects. Their starting centers define wheel contact locations. Set wheel radius and dimensions in a `SkateProfile`.
4. For a complete authored board, disable `GenerateGeometry`, keep your model hierarchy, and provide a deck collider. Optional front/rear foot targets use the avatar's ankle-bone position and orientation, rather than a sole-aligned frame; the rider preserves these authored transforms. Generated targets use the model's ankle bind pose and adapt to regular/goofy stance.
5. Put `SkateRider` on a separate object and assign its `Board`. It creates the default Citizen avatar and takes over local controls. Bind `SkateMount` to dismount/remount (E in the lab), `SkatePickup` to pick up/drop (F), and `SkateBail` for a voluntary bail (B). Walk with movement input while off the board (hold `SkateSprint` to sprint while running; Shift in the lab, the same key as pump on the board); E recovers a settled ragdoll when there is standing room.
6. Bind `SkateManual` and `SkateNoseManual` for keyboard balance (M/N in the lab). On a controller, hold the right stick partway down/up. Full stick deflection remains the trick windup. On keyboard and mouse, bind `SkateFlick` (right mouse in the lab): while it is held the mouse is the trick stick, so pull down to crouch and flick up, or up and to a side, to pop. Without the mouse, hold Jump and release it, with `SkateFlipLeft`/`SkateFlipRight` (Z/C in the lab) held for a kickflip or heelflip. Hold `SkateSlide` to powerslide and tap it to revert; hold `SkatePush` and `SkateBrake` together, then let go, to hippy jump (both push buttons on a controller). In the air, hold a grab with `SkatePush` or `SkateBrake` (the left stick on a controller) to front or back flip, and hold `SkatePump` before a transition and let go in it to pump (`SkateProfile.AutoPump` also pumps a little without the button as the ground flattens; `SkateProfile.Difficulty` picks Easy, Normal or Hard handling). Steering keys ramp the trucks in and out like a stick, walking follows the camera, and `SkateCamera` orbits with the mouse. Keyboard and mouse and a controller work together at any time: a held key or the mouse drives its control, otherwise a stick or trigger pushed past drift does.
7. Add `GrindRail` to any rail, ledge or coping. With a `BoxCollider` on the same object it grinds along the box's top (center line when narrow, both long edges when wide); otherwise list local `Points`. Ollie onto it: trucks over the rail give a 50-50, 5-0 or nosegrind, a deck across it gives a boardslide.
8. Bind `SkatePump` (Ctrl / left trigger in the lab) and hold it through the bottom of a transition to gain speed.
9. For clip animation, put a clip set (`.sman`) and its graph (`.json`) in your game's data folder and set `SkateRider.AnimationClips` / `AnimationGraph` to their paths. The rider then plays and retargets those clips onto its model from gameplay; leave them empty for the built-in animation. No clips ship with the library. The formats are described under How it works. Bind `SkateGrabFront`/`SkateGrabBack` for air grabs (steering picks nose/tail variants, both together a crail) and `SkateGesture` to cycle the graph's gestures.
10. Optional tools: `SkateDebugger` draws wheel, deck and contact state while playing; `SkateReplay` records inputs and replays them from the same start, reporting the largest deviation.
11. Open the separate `skate-motion-lab` game for the collision-mesh course, rail and repeatable recorder.

### In code

```csharp
using SkateMotion;

var board = Skating.Create( Scene, new Transform( spawnPosition ) );
board.SetInput( new SkateInput( Push: 1f, Steer: 0.2f ) );
```

Tricks come from the right stick: pull back and flick for an ollie, kickflip, heelflip or shuvit; rolling the stick sideways during the pull-back adds board spin (more than one stick width of travel gives a varial, hardflip or inward heelflip by direction; more than 2.2 the 360 versions). `TrickStarted` reports which.

For a manual, hold `new SkateInput( FlickY: -0.45f )`; use `+0.45f` for a nose manual and zero to release. `board.State.Balance` reports `Manual` or `NoseManual` only when the opposite axle is physically raised. The current estimated balance window is 0.2-0.6 stick deflection with horizontal deflection below 0.25.

Set `board.BoardModel = Model.Load( "models/skateboard.vmdl" );` to ride any skateboard model (changing it while running rebuilds the board); `board.Dimensions` then reports the measured wheelbase, track, wheel radius and ride height and how the parts were found, and `board.Lean` how far the deck dips into the current turn (radians, positive with its left side down).

`Skating.CreateRail( Scene, start, end )` adds a grind rail from code. Subscribe to `TrickStarted`, `Landed`, `GrindStarted`, `GrindEnded`, `Collided` and `Bailed` on the board; `board.State.Grind` reports the current grind.

With a clip set loaded, `rider.PlayAnimation( new Dictionary<string, string> { ["family"] = "gesture", ["action"] = "wave" }, 2f )` plays any tagged motion for two seconds; `rider.AnimationState` names the playing graph state and `rider.AnimationMotion` the playing clip. `rider.AnimationActions( "gesture" )` lists what a family offers, and `rider.NextGesture()` plays the next one. `SkateInput.Grab` (`SkateAirGrab`) selects an air grab; it changes only the animation.

After startup, call `board.CaptureTelemetry()` for an allocated diagnostic snapshot of all seven physical parts, contact geometry, maximum joint error and kinetic energy. Positions and velocities in this snapshot use metres and seconds, angular velocities use radians per second, and energy uses joules. Contacts describe the final substep before integration; body states describe its result. This API returns null before startup and does not allocate unless called.

## How it works

Internal version 2 through 5 pose readers retain raw float32 rotations, scale, masks and separate reference poses. Version 3 additionally preserves cycle translation, cycle rotation and the trajectory track; version 4 also retains signed-time pose streams and their paired names. Version 5 adds continuous key sampling with its own ordered interpolation, while older files retain block sampling. Native checks cover two user-supplied auxiliary banks and 132 poses with 26,928 exact transform-word comparisons; the existing 3,324 block clips also pass regression checks. Interval sampling uses previous/current times and wrap history to produce a motion delta, then composes the selected reference once. Older clips with unknown trajectory or stream data require an explicit format upgrade before using those features. Auxiliary reference composition now passes eight native pose comparisons with 3,264 exact reference/composed float words; scalar quaternion addition follows the stored axis order after conversion, also passing 32,256 converted-axis composition values. An indexed auxiliary pose cache now preserves discrete frame-clock rounding and feeds command-buffer snapshots; both banks match all 25,296 captured pose values and 25,296 snapshot values in native checks. Indexed stream playback now blends cached local poses, composes the selected reference once and uses the reference directly for missing streams. Native checks cover 100 joined cases and 20,400 exact values, including paired selection and sample limits. Quaternion blend reductions preserve stored lane order after axis conversion. Multi-input stream queues now retain one weight per sampled input and preserve the distinct duplicate-value reduction rule across all three slots. Native comparisons cover 60 cases, 120 traversals and 6,504 command words with one through five inputs. Reusable sequence, transition, channel and directional nodes now connect their clocks to body preparation and auxiliary stream traversal. Native checks replay 96 nested-tree cases and match all 5,094 command words through production nodes; body preparation, handoff, context separation and allocation behavior have additional regressions. Complete pose trees now use the retained channel ownership lifecycle: interrupted replacements promote the successor before release, and reused composites rebind body and stream children together. All 128 native ownership snapshots pass; connected body/stream replacement scenarios have additional regressions. Constant references and composition wrappers now participate in these pose trees, restoring raw inputs on preparation while forwarding only the active child's clock and auxiliary commands. Native checks cover 175 composed body samples and 96 nested stream cases. The character still uses the earlier clip path; live model mapping, graph scheduling and renderer integration remain unfinished.

Map collision is gathered only around the board: the shapes of bodies within 12 m of it, gathered again once it has travelled 4 m, and each physics step offers only the triangles within 2 m of its parts. A large shape (a level's world mesh) gets a grid over its triangles, which the board's wheel sweeps and contacts share; its triangles are read once, so the board's cost follows what is near it, not the size of the map.

Cached scene mesh, hull and heightfield triangles now generate the board's live physical contacts from seven current body snapshots and motion-aware bounds. Wheels use spheres and trucks use longitudinal capsules; the wheel radius still comes from the caller's profile. Unset shape friction inherits its surface, while an explicit zero remains frictionless. Generated map contacts and retained native prop/rail contacts share one integration step; stationary keyframed map colliders are included. Four sphere traces and deck sweeps still supply the current pilot's support and initial-overlap recovery. Contact, joint, drive and body-update routines simulate the deck, two trucks and four wheels at up to 1/240-second steps. The native rigidbody supplies queryable deck geometry; its integration and solid contact response are disabled while the board solver owns motion and transfers impulses to dynamic surfaces. Disabling the adapter restores the original native contact flags. Grind rails add contacts at each truck axle, with side contacts that keep the rail between the wheels, or at the deck for boardslides; they use grind friction, and the rider balances over the rail with steering. Pumping applies the work of extending the legs against the centripetal load, so it only adds speed on curved surfaces. Native character movement handles walking and carrying, and a bail hands the rider's incoming motion to a native ragdoll while unloading the board.

Clip animation: a clip set is a little-endian binary ("SMAN", version 1) holding a bone hierarchy with rest pose and per-bone keys in metres, Z up, X forward; the graph JSON tags every clip (family, action, phase, style, side, height, lean, speed, strength, direction, detail, kind) and lists states in priority order. Each frame the rider publishes gameplay as parameters, the graph picks the best-matching tagged motion (required family/action/phase, preferred categories matched by word, unrequested qualifiers losing ties; crossfading, rotating variants, blending lean by steering). A looping activity plays its intro, its cycle, and its exit before the next activity; urgent changes such as leaving the ground cut exits short. Recovery from a bail plays a get-up chosen from how the ragdoll lies, fast dismounts run out, and deck impacts play a knock; and the pose is retargeted onto the avatar: rotation changes from rest plus a swing that points every limb where the source limb points, so differing rest poses add no error. Any humanoid model works: its hips, spine, neck, head, arms and legs are found from known rig naming (s&box, Mixamo, Unreal, Character Creator, DAZ, Rigify, VRM, 3ds Max Biped, Auto-Rig Pro, Advanced Skeleton, mocap formats), then from word matching, then from the hierarchy alone; its facing and leg length are measured from the rest pose, A-pose arms are swung to match, and hands stay straight on the forearm. Set `SkateRider.CharacterModel` to use one; a model without recognisable legs, hips and head keeps the built-in animation. Two-bone leg IK keeps soles on the deck or ground. Riding foot placement preserves the animated knee bend plane instead of forcing it toward the toes. Optional `ClipLooping` graph entries let one-shot clips hold their last pose through a fade, including individual leaves inside blends. The clip root follows the deck on the ground and only the board's heading in the air. A graph may declare its clips' stance; riders in the other stance are mirrored.

Blends and state graphs: a graph may also define named blends (1-D blends along a parameter at the values its clips were authored for, keyed selects and threshold switches) that motions can name like clips; they mix their clips in phase from parameters the rider publishes (lean -1..1, crouch as the centre-of-mass height in metres, speed in m/s, push effort and speed 0..1). It may also carry a hierarchical state graph that decides what plays, replacing the tagged states: each state has entry/staying tests (intents such as left-push, brake, manual or ollie-anticipation; physics state; grind; speed; "clip ends within t"; previous state), plays a clip or blend with mirror and switch-stance alternatives, and lists transitions. A state is entered when its tests pass and one of its active children can be entered down to a leaf; transitions also need their target to be enterable; a current state that may not be interrupted keeps its whole path, and otherwise earlier guarded siblings take over from interruptible states. A single held pose lasts as long as its fade. A graph may name turn-round clips in `StanceSwapClips`: each start of one swaps the rider into or out of switch (rolling backwards then counts as forwards), and later clips play mirrored and facing the board's tail. Board-relative helper bones drive the feet when supplied by a clip set; otherwise mapped toe bones are used. The pull fades during states that release the feet. Walking uses its own input and speed, and board possession selects the carrying variants. Named condition arguments distinguish gait categories; gait speed thresholds, foot blending and continuous tilt smoothing remain estimates.

A clip graph can set `CarryHand` to `left_hand` or `right_hand`, identifying the hand in its authored
stance. While carrying, the board follows that hand's retargeted position and the clip's board orientation;
the other stance mirrors both together. `AnchorBone` supplies the board track. An empty `CarryHand` or a
missing mapped hand keeps the fallback carry pose. This adapts the authored wrist-to-board displacement
to the avatar's size; board-specific grip sockets and finger posing are not yet provided.

Board models: `Skateboard.BoardModel` reads the model's first level of detail and finds its parts from its geometry. It lies along its longest side with the deck on top, and a board far shorter or longer than a deck (authored in other units) is shown 0.8 m long, and one wider than any deck (over 0.30 m) 0.25 m wide. The deck's cross-section at the board's middle gives its width, thickness and underside; the lowest points at each corner are the wheels' treads, and the connected piece holding each one is that wheel when it is round seen along its axle and fits under the deck (bearings and cores inside its outline go with it); otherwise the wheel is fitted from the tread and the points above it. Other pieces sitting at or above the deck's underside are the deck's; pieces under it near an axle are that truck's: the one reaching across to the wheels is the hanger, pieces reaching up to the deck are the baseplate, and the rest go with whichever of the two they are nearer. A piece holding several parts (a model welded into one mesh, or a truck welded to its wheels) is split triangle by triangle by where each lies. Each part becomes its own model about where it turns (a wheel about its centre, a hanger about its axle), keeping the model's materials, so it moves on its own. A model with a bone for each wheel (named for wheels, or right at their centres) is drawn whole and moved by its bones; truck bones move the trucks. The board's physics uses the measured wheel centres, wheel radius and ride height, and the deck's shape for the feet comes from the deck's own triangles. Detection was checked on four cloud boards (popsicle decks 0.96 m and 1.05 m long, a 1.5 m longboard modelled along its Y axis, and one of 125,000 triangles at 2.5 times scale; a hoverboard is refused for having no wheels) and on synthetic boards made of separate pieces, welded into one mesh, with the wheels welded to the trucks, turned every way and rigged.

Deck lean: steering asks each truck to twist about its pivot, an axis rising steeply from the deck, so the deck rolls over the hangers while the wheels stay on the ground. The twist follows the steering through the stick and speed response curves (scaled by the stick again, so half steer leans little), eases while pushing and in a manual, is filtered as the stick and the deck take it up, and eases into the truck's 14 degree twist, whose roll share leans the deck at most 12 degrees. Off the ground the trucks keep 0.983 of their twist each sixtieth of a second and take the deck's up again over 0.165 s after landing; on rails, in powerslides, reverts, wall rides and hand plants, and after a bail the deck settles level. The lean is shown, not simulated: the deck pivots about the line through the trucks' pivots (where the hanger meets the baseplate), the shown hangers and wheels stay where physics holds them, and the rider's animation root follows the leaning deck. Wheels turn at their rolling speed along their truck over their radius while on the ground and spin on in the air, on a rail and lifted in a manual, losing 0.36 of their spin a second.

Animation on any board: the clips were made on one board (`AnimationGraphDefinition.Board`, a `ClipBoardDefinition`; 0.486 m wheelbase, 0.902 m long, 0.24 m wide and 15 mm thick unless set), and every place they give against it is moved onto the board ridden, as measured: along the deck piecewise (middle to truck, truck to end, past the end unchanged), across it by its width, and up by how far the place is over the deck's top or under its underside. Feet follow the trucks as far as a rider stands (a stance at most 25% wider or 20% narrower than the clips') and are fitted across to the deck's own edges where they stand, so a deck tapering toward its ends keeps them on it; a carried board's thumb stays on the deck's top and its fingers under it, at any thickness; landing, a foot that comes down on the deck stays where it came down for 0.6 s, then steps to its place; a hand on the board reaches the board's own nose, tail or edge, easing in as the clip's hand comes within 8 cm of its board; a carried board is moved so the hand grips the same place on it. The deck collides at the model's own width and thickness, and as long as a flat deck whose ends meet level ground at the same tip onto a truck as its kicked-up nose and tail do, so a long kicked deck does not strike its tail early; on a rail its whole length counts, kicks included. Parts drawn with more than 3,000 triangles keep rails and the ground off a cheaper stand-in on or just outside their surface. Getting on, a stepping foot that meets a longer deck's kicked tail early rises onto it over a few frames; a pushing foot goes as far past the deck's edge as the clip has it past its own and is put down on the ground however high the deck stands; and a board shown on its back or side rests on the ground on its kicked nose and tail.

Camera: `SkateCamera` follows the board and rider as shown each frame. Riding, it settles behind the way the board travels (not the way it faces, so fakie, reverts, powerslides and flips never swing it) with a lazy, overdamped turn, holds its height through ollies and follows drops down, frames grinds lower and manuals closer, and follows a bail's ragdoll softly. Probes ahead along the travel raise it to look down into drops. Sweeps from the focus, head height and feet keep it out of the world: it cranes up over what blocks its usual place and pulls in, early with a wider probe, counting the way as blocked only when all three are, so thin poles do not pull it in. The mouse turns it directly through the engine's look input; riding, it eases back behind the board once the mouse rests, and on foot it never turns by itself. Its followers are integrated in sub-steps, so any frame rate gives the same path.

## Multiplayer

Single-player, host and client are supported for riding. A board is simulated by its network owner, or by the host when it has none: give the rider ownership (`GameObject.Network.AssignOwnership`) and the rider's own client simulates the board it rides, with no round trip for its input and no cost to the host, which then pays only for boards nobody owns. A peer that takes a board over carries on from where the board was last seen. Input set where the board is not simulated is forwarded to its owner, which accepts it only from the board's driver (`SetDriver`, host only, set automatically to a networked `SkateRider`'s owner). Speed, wheel count, airborne, bail, balance, grind and the bail's release velocity sync from whoever simulates the board; the transform uses s&box network interpolation. Events fire where the board is simulated. A board no one rides that has lain still for a second falls asleep (`Skateboard.Asleep`) and costs nothing until it is ridden, moved or reset. Another player's rider far from the camera is posed less often (every second frame from 12 m, every fourth from 24 m, every eighth from 48 m). Another player's rider walks, carries and rides as its owner does: the owner's mode is shared and its walk is shown from how fast its synced place moves. Host plus `-joinlocal` client tests pass for both models: with the host simulating, client input drives the host board and the client's synced speed stays within 0.16 m/s; with the client owning the board and its rider, it pushes its own board to 8.5 m/s, the host's synced speed stays within 0.13 m/s of it (190 ms behind at most), and its bail reaches the host as a ragdoll. Walking and carrying are not yet verified over the network, and proxies do not animate wheel spin, truck steering or deck lean.

## Limitations

The internal overlay factory now constructs supported authored motions, applies rate before owner
wrappers, and releases parameter ownership with channel storage. Owner reference order and posture
requests retain their source behavior. Posture wrappers now apply explicit authored bone pairs,
attribute-name mappings and auxiliary pairing together. Manual, trick and powerslide flags follow
compiled entry/exit lifecycles, and the retained riding-direction updater preserves its timing gates.
Graphs can name a `PostureProfilePath`; the asset loader validates its resolved maps against the
clip skeleton before exposing the posture provider. Explicitly unpaired bones remain unchanged.
Base-tree construction now consumes eligible indexed references before applying owner references
and posture, then lets the retained owner set rate and publish the root. The movement classifier
feeds physical riding observations and the retained direction updater. Completed support and edge
results now produce ordered ground samples, refine them and feed admission and final selection.
Playback context shares actor flags, selectors, held-board feedback and the same pending indexed
reference used by base construction. Graph scalar assignments and trick height now share their
ordered physical queue; phase assignments can also replace animation overrides. Physical mode
entry updates the retained character field. Intent bindings now forward exact request values to
that shared output. Body-tilt instances share actor flags and preserve activation-dependent smoothing
before writing animation overrides. Contact history now resolves initialized metadata and feeds the
movement classifier. Separate owner timers now consume the graph clock and retained teleport state.
Compiled behavior registration now keeps independent instance families distinct, forwards retained
references and rejects missing bindings before graph construction. Tilt instances release their
state with their final retained reference. Kickturn guards and resets share the owner timer.
Ground probe submission now runs through cached engine meshes and the complete
support-selection pipeline, preserving batch capacity and failed submission behavior. World selection,
registered-edge providers, raw physical input production and complete compiled actor wiring remain
unfinished. The recovered schedule reads
retained physical observations during graph updates, before the next physical input and output phases.
